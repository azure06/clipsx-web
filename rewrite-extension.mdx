Build the first-party `infiniti.rewrite` source and run it locally. You will finish
with a `.clipsx` archive and a transformation result attached to a harmless sample
clip. This is a guided build of an existing package; use it to learn the contract
before making a new package with your own identity.

## Prerequisites {#prerequisites}

- Git, Node.js with npm, and [Rust installed through rustup](https://rust-lang.org/tools/install/).
- The native [Tauri build prerequisites](https://v2.tauri.app/start/prerequisites/) for your operating system: the wrapper builds a tool from the desktop repository.
- A ClipsX desktop build compatible with Extension API v3.2. Confirm that the source tooling and installed app support the same contract; a newer source checkout does not upgrade your installed app. Check the [extension contract](https://github.com/azure06/clipsx/blob/main/docs/EXTENSION_API_V3.md) and [available desktop builds](https://clipsx.app/en/download).
- A working generation model for the runtime exercise. Follow [Local AI setup](/local-ai#generation-models). Building and validating the archive does not require Ollama to be running.

Add the guest compilation target:

```sh
rustup target add wasm32-unknown-unknown
```

The guest uses the pinned no-WASI contract. Keep `sdk/wit/clipsx-extension.wit`
and the host WIT aligned; do not change the API version to bypass compatibility errors.

## Get the source {#source}

Run these commands in a new working directory. The two checkouts must be siblings
for the default wrapper to locate the host:

```sh
git clone https://github.com/azure06/clipsx.git
git clone https://github.com/azure06/clipsx-extensions.git
cd clipsx-extensions
npm ci
```

Use revisions that support the same contract. For reproducible builds, record
`git rev-parse HEAD` in each checkout. This guide does not require building or
releasing a new desktop installer.

If your host checkout is elsewhere, set `CLIPSX_REPO` to its absolute path in the
current shell before running package commands:

<CodeGroup>

```powershell PowerShell
$env:CLIPSX_REPO = 'C:\path\to\clipsx'
```

```sh macOS or Linux
export CLIPSX_REPO=/path/to/clipsx
```

</CodeGroup>

## Build and validate the archive {#build}

From the `clipsx-extensions` checkout:

```sh
npm run package -- rewrite dist/rewrite-local.clipsx
```

The script runs the guest's Rust tests, builds its release WASM, copies it to the
package root, packs twice to check deterministic bytes, and runs archive
validation, inspection, and component checks. The first host-tool build may take
longer and use substantial disk space. A successful run prints the package ID,
version, output filename, and SHA-256 digest.

Inspect or recheck the exact archive:

```sh
npm run tool -- inspect dist/rewrite-local.clipsx
npm run tool -- validate dist/rewrite-local.clipsx
npm run tool -- test dist/rewrite-local.clipsx
```

The `test` command checks compatibility, manifest, assets, limits, and component
structure. It does not run the model or verify a desktop interaction. The output
archive is a local development artifact, not a published or signed release.

## Import it into ClipsX {#install}

1. Open **Settings → Extensions → Developer**.
2. Enable **Allow local packages**.
3. Choose **Install local .clipsx package** and select `dist/rewrite-local.clipsx`.
4. Read the requested permissions before consenting. Rewrite requests selected input and generation; it also declares capabilities for optional copy-triggered automation.
5. Find **Rewrite** under **Installed** and ensure it is enabled.

The package ID is still `infiniti.rewrite`. If you already have the registry
version installed, this is the same package identity, not a separate demo. Review
the existing installation before replacing it.
Developer Mode permits unsigned packages; leave it off when you no longer need
local imports. Existing permissions still apply.

## Verify a first result {#first-result}

1. In **Intelligence → Models**, verify that **Local Text Generation** is enabled with an installed generation-capable model.
2. Copy this harmless sample:

```text
hey can you send the updated diagram before friday? need it for the review
```

3. Open the clip and choose **Rewrite**, then **Business**.
4. Run the transformation. Inspect the result and compare it with **Original**.
5. Copy the result deliberately, or choose **Save as new clip** to keep an independent clip.

Success means a completed result is attached to the source and remains accessible
after reopening the clip. Expect a more formal version of the request, but not
specific wording: output depends on the model and may change meaning. Check it
before using it. Running a transformation does not automatically replace the
system clipboard. Deleting the source also removes its attached results.

Automatic rules are optional and are not needed for this exercise. If you enable
them later, use a narrow application scope and harmless content first. They apply
to accepted new copies, not a replay of old history.

## Understand and change the example {#customize}

Read these source files before changing behavior:

- [Manifest](https://github.com/azure06/clipsx-extensions/blob/main/extensions/rewrite/clipsx-extension.toml): package identity, permissions, the transformer, parameters, named setups, and activation.
- [Rust guest](https://github.com/azure06/clipsx-extensions/blob/main/extensions/rewrite/src/lib.rs): generation requests, validation, output, and tests.
- [Pinned WIT](https://github.com/azure06/clipsx-extensions/blob/main/sdk/wit/clipsx-extension.wit): the guest/host interface.

Start without a source change: use **Custom** with the instruction “Keep technical
terms unchanged and make the request concise.” To change the guest, modify one
behavior, add a relevant Rust test, rebuild the archive, and import the new bytes.
Review permissions again when prompted.

The host chooses the configured provider and keeps its endpoint, model, and
credentials out of the guest. The package returns a named result; the host owns
jobs, result storage, Copy, Paste, Regenerate, and Save controls. Do not add direct
clipboard writes or store generated output in package state.

When creating a different extension, choose your own package ID and metadata;
keep the first-party identity only for studying this example. The repository's
`package` script is limited to its listed first-party packages. New packages use
the host CLI's `pack`, `validate`, `inspect`, and `test` commands described in the
[contract](https://github.com/azure06/clipsx/blob/main/docs/EXTENSION_API_V3.md#build-and-publication).

## Recover from common failures {#recovery}

| Symptom | What to check |
| --- | --- |
| Host checkout not found | Keep the checkouts as siblings or set `CLIPSX_REPO` to the absolute host path. |
| Missing WASM target | Run `rustup target add wasm32-unknown-unknown` and retry the build. |
| Native compilation or linker error | Check your OS-specific Rust/Tauri prerequisites and the first build error. |
| Manifest, WIT, or compatibility error | Align source and host revisions. Rebuild with the pinned WIT instead of editing version numbers to force installation. |
| Local import control is missing | Open the Developer section and enable Allow local packages. Check that your installed host supports this contract. |
| Model unavailable or generation fails | Verify the connection, installed model, and enabled generation capability in [Local AI](/local-ai#recovery). |
| Result is wrong or incomplete | Review the input and model response, simplify the task, and check reported context or output limits. Do not treat generated text as verified. |
| Package is quarantined | Inspect its diagnostics and fix the failure before retrying. See [extension recovery](/extensions#recovery). |

## Local testing and distribution {#distribution}

Before distributing a change, test manual execution, cancellation, missing-model
recovery, restart, source deletion, and saving a result as an independent clip.
If you implement automation, also test rule consent, source scope, and that
execution never automatically writes to the system clipboard.

Public distribution is a separate process: immutable release archives,
checksum and permission metadata, and catalog review and signing. A successful
local build does not grant registry publication or certify platform behavior.
Follow the [extension repository instructions](https://github.com/azure06/clipsx-extensions#release-flow)
and [registry instructions](https://github.com/azure06/clipsx-registry) before
proposing a release. Validation and signatures do not guarantee package safety.
